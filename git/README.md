## Как устроен Git

Файл проходит три зоны:

```text
рабочий каталог --git add--> индекс --git commit--> локальный репозиторий --git push--> удалённый репозиторий
                                                    локальный репозиторий <--git fetch-- удалённый репозиторий
рабочий каталог <------git switch, git restore----- локальный репозиторий
                        git pull = git fetch + git merge (или rebase)
```

- **Рабочий каталог** — файлы, которые вы редактируете.
- **Индекс** — то, что войдёт в следующий коммит.
- **Коммит** — снимок проекта с автором, сообщением и ссылкой на родителя.
- **Ветка** — подвижный указатель на коммит. `HEAD` — указатель на текущую ветку или коммит.
- **origin/main** — локальная копия состояния ветки `main` на удалённом репозитории `origin`. Обновляется командой `git fetch`.

## Настройка

| Команда | Назначение | Пример | Важные замечания |
|---|---|---|---|
| `git config --global user.name` | Имя автора коммитов | `git config --global user.name "Сергей Иванов"` | Без `--global` настройка действует только для текущего репозитория |
| `git config --global user.email` | Email автора | `git config --global user.email "sergey@example.com"` | Должен совпадать с email в аккаунте GitHub или GitLab, иначе коммиты не привяжутся к профилю |
| `init.defaultBranch` | Имя ветки по умолчанию для новых репозиториев | `git config --global init.defaultBranch main` | |
| `core.autocrlf` | Преобразование окончаний строк | Windows: `git config --global core.autocrlf true`; Linux, WSL, macOS: `input` | Надёжнее зафиксировать правила в `.gitattributes` репозитория |
| `core.editor` | Редактор для сообщений коммитов | `git config --global core.editor "code --wait"` | Без `--wait` редактор сразу вернёт управление, и коммит прервётся с пустым сообщением |
| `pull.rebase` | Поведение `git pull` при расхождении веток | `git config --global pull.rebase false` | `false` — слияние, `true` — rebase. Альтернатива: `pull.ff only` разрешает только fast-forward |
| `merge.conflictStyle` | Показывать общего предка в конфликтах | `git config --global merge.conflictStyle zdiff3` | `zdiff3` — с Git 2.35; на более старых версиях используйте `diff3` |
| `alias.*` | Короткие команды | `git config --global alias.lg "log --oneline --graph --all --decorate"` | Использование: `git lg` |
| `git config --list --show-origin` | Все настройки и файлы, откуда они взяты | `git config --list --show-origin` | Помогает найти, где задано «странное» значение |

## init и clone

| Команда | Назначение | Пример | Важные замечания |
|---|---|---|---|
| `git init` | Создать репозиторий в текущем каталоге | `git init -b main` | Создаёт скрытый каталог `.git`. ⚠️ Удалив `.git`, вы потеряете всю локальную историю |
| `git clone URL` | Скопировать удалённый репозиторий | `git clone https://github.com/user/repo.git` | Создаёт каталог с именем репозитория и настраивает remote `origin` |
| `git clone URL каталог` | Клонировать в указанный каталог | `git clone git@github.com:user/repo.git my-repo` | Адрес `git@...` — SSH (нужен ключ), `https://...` — токен или Credential Manager |
| `git clone --depth 1` | Только последний коммит | `git clone --depth 1 URL` | Быстро, но история неполная. Дополнить её: `git fetch --unshallow` |
| `git clone -b ветка` | Сразу нужная ветка | `git clone -b develop URL` | |

## status add commit

| Команда | Назначение | Пример | Важные замечания |
|---|---|---|---|
| `git status` | Что изменено, что в индексе, что не отслеживается | `git status` | Самая полезная команда: запускайте её перед каждым `add`, `commit`, `reset` |
| `git status -sb` | Краткий формат | `git status -sb` | Колонки: левая — индекс, правая — рабочий каталог. `??` — неотслеживаемый файл |
| `git add файл` | Добавить изменения в индекс | `git add src/app.py` | |
| `git add .` / `git add -A` | Добавить всё | `git add -A` | Перед этим проверьте `git status`: легко закоммитить `.env`, логи и мусор |
| `git add -p` | Добавлять по частям (интерактивно) | `git add -p app.py` | `y` — добавить часть, `n` — пропустить, `s` — разбить на меньшие части, `q` — выйти |
| `git commit -m` | Создать коммит | `git commit -m "Добавить проверку email"` | Сообщение пишут в повелительном наклонении и кратко объясняют, **что** и **зачем** |
| `git commit` | Коммит с сообщением в редакторе | `git commit` | Первая строка — до ~50 символов, пустая строка, затем подробности |
| `git commit -am` | Добавить изменённые отслеживаемые файлы и закоммитить | `git commit -am "Исправить опечатку"` | Новые (неотслеживаемые) файлы **не** добавляет |
| `git commit --amend` | Исправить последний коммит | `git commit --amend --no-edit` | ⚠️ **Опасно:** создаёт новый коммит вместо старого. Если старый уже запушен, понадобится force push |
| `git rm` | Удалить файл из репозитория и с диска | `git rm old.py` | ⚠️ **Опасно:** удаляет файл с диска. Чтобы убрать файл только из Git, оставив на диске: `git rm --cached` |
| `git rm --cached` | Перестать отслеживать файл | `git rm --cached .env` | Затем добавьте файл в `.gitignore`. Из старых коммитов он не исчезнет |
| `git mv` | Переименовать файл | `git mv old.py new.py` | |

## log и show

| Команда | Назначение | Пример | Важные замечания |
|---|---|---|---|
| `git log` | История коммитов | `git log` | Выход из просмотра — `q` |
| `--oneline --graph --all` | Компактный граф всех веток | `git log --oneline --graph --all --decorate` | Лучший способ увидеть, как расходятся ветки |
| `-n N` | Последние N коммитов | `git log -n 5` | |
| `-p` / `--stat` | С диффом / со статистикой файлов | `git log -p -n 1` | |
| `-- путь` | История конкретного файла | `git log --follow -- src/app.py` | `--follow` продолжает историю через переименования |
| `--author` / `--since` / `--until` | Фильтры | `git log --author="Сергей" --since="2 weeks ago"` | |
| `--grep` | Поиск по сообщениям коммитов | `git log --grep="fix" -i` | |
| `-S "текст"` | Коммиты, где текст появился или исчез | `git log -S "API_KEY" --oneline` | Помогает найти, когда добавили или удалили строку |
| `A..B` | Коммиты из `B`, которых нет в `A` | `git log main..feature --oneline` | Что войдёт в `main` при слиянии `feature` |
| `git show` | Показать коммит | `git show HEAD~1` | `git show HEAD:path/file` — файл в том виде, каким он был в коммите |
| `git blame` | Кто и когда менял каждую строку | `git blame -L 10,30 src/app.py` | |
| `HEAD~N` / `HEAD^` | Относительные ссылки | `HEAD~2` — два коммита назад | `HEAD^2` — второй родитель merge-коммита |

## diff

| Команда | Назначение | Пример | Важные замечания |
|---|---|---|---|
| `git diff` | Изменения в рабочем каталоге, ещё не добавленные в индекс | `git diff` | Неотслеживаемые файлы не показываются |
| `git diff --staged` | Что уйдёт в следующий коммит | `git diff --staged` | Синоним — `--cached`. Проверяйте перед каждым коммитом |
| `git diff HEAD` | Все незакоммиченные изменения | `git diff HEAD` | |
| `git diff A B` | Разница между коммитами или ветками | `git diff main feature` | |
| `git diff A...B` | Изменения в `B` с момента ответвления от `A` | `git diff main...feature` | Так выглядит дифф Pull Request |
| `--stat` / `--name-only` | Только список файлов | `git diff --stat main` | |
| `--word-diff` | Разница по словам | `git diff --word-diff README.md` | Удобно для текстов |
| `-- путь` | Ограничить файлами | `git diff -- src/` | |

## branch и switch

| Команда | Назначение | Пример | Важные замечания |
|---|---|---|---|
| `git branch` | Список локальных веток | `git branch -vv` | `-vv` показывает отслеживаемую удалённую ветку и отставание |
| `git branch -a` | Все ветки, включая удалённые | `git branch -a` | Удалённые ветки обновляются через `git fetch` |
| `git branch имя` | Создать ветку, не переключаясь | `git branch hotfix` | |
| `git switch имя` | Переключиться на ветку | `git switch main` | Если в рабочем каталоге есть изменения, которые конфликтуют с веткой, Git откажется переключаться |
| `git switch -c имя` | Создать ветку и переключиться | `git switch -c feature/login` | Старый аналог: `git checkout -b` |
| `git switch -c имя origin/имя` | Взять ветку с удалённого репозитория | `git switch -c fix origin/fix` | Обычно достаточно `git switch fix`: Git сам найдёт `origin/fix` |
| `git switch -` | Вернуться на предыдущую ветку | `git switch -` | |
| `git switch --detach` | Перейти на конкретный коммит | `git switch --detach a1b2c3d` | Это состояние «detached HEAD». Новые коммиты сохраните в ветку: `git switch -c имя` |
| `git branch -m` | Переименовать ветку | `git branch -m old-name new-name` | |
| `git branch -d` | Удалить влитую ветку | `git branch -d feature/login` | Безопасно: откажется удалять невлитую ветку |
| `git branch -D` | Удалить ветку принудительно | `git branch -D experiment` | ⚠️ **Опасно:** невлитые коммиты останутся только в `reflog`, который со временем очищается |
| `git checkout` | Устаревшая универсальная команда | `git checkout main` | Совмещает `switch` и `restore`. ⚠️ `git checkout -- файл` молча отбрасывает изменения в файле |

## merge

| Команда | Назначение | Пример | Важные замечания |
|---|---|---|---|
| `git merge ветка` | Влить ветку в текущую | `git switch main && git merge feature` | Если `main` не ушла вперёд, произойдёт fast-forward без merge-коммита |
| `--no-ff` | Всегда создавать merge-коммит | `git merge --no-ff feature` | В истории видно, что изменения пришли одной веткой |
| `--ff-only` | Только fast-forward, иначе ошибка | `git merge --ff-only origin/main` | Безопасное обновление ветки без лишних merge-коммитов |
| `--squash` | Собрать изменения ветки в один коммит | `git merge --squash feature && git commit` | Коммит не связан с веткой, поэтому `git branch -d feature` откажется её удалять |
| `--abort` | Отменить слияние с конфликтами | `git merge --abort` | Возвращает состояние до `merge`. Изменения, сделанные во время разрешения конфликта, будут потеряны |
| `--continue` | Завершить слияние после разрешения конфликтов | `git merge --continue` | То же, что `git commit` |

## rebase

`rebase` переносит ваши коммиты поверх другой ветки, создавая **новые** коммиты с другими хешами. История становится линейной.

> [!CAUTION]
> Золотое правило: не делайте rebase коммитов, которые уже запушены в общую ветку, где с ними работают другие. Их история разойдётся с вашей, и им придётся вручную распутывать дубликаты.

| Команда | Назначение | Пример | Важные замечания |
|---|---|---|---|
| `git rebase ветка` | Перенести текущую ветку на вершину другой | `git switch feature && git rebase main` | ⚠️ **Опасно:** переписывает историю. После этого запушенная ветка требует `push --force-with-lease` |
| `git rebase -i HEAD~N` | Интерактивно отредактировать последние N коммитов | `git rebase -i HEAD~3` | ⚠️ Переписывает историю. В редакторе: `pick` — оставить, `reword` — изменить сообщение, `squash`/`fixup` — склеить с предыдущим, `drop` — удалить коммит |
| `--continue` | Продолжить после разрешения конфликта | `git add файл && git rebase --continue` | Конфликт может появиться на каждом переносимом коммите |
| `--abort` | Отменить весь rebase | `git rebase --abort` | Возвращает ветку в исходное состояние |
| `--skip` | Пропустить текущий коммит | `git rebase --skip` | ⚠️ Изменения этого коммита не попадут в результат |
| `commit --fixup` + `--autosquash` | Исправить старый коммит | `git commit --fixup a1b2c3d && git rebase -i --autosquash main` | Исправление автоматически встанет после нужного коммита |
| `--onto` | Перенести часть ветки на другую базу | `git rebase --onto main old-base feature` | Нужен, когда ветка была создана не от той базы |
| `git pull --rebase` | Получить изменения и переложить свои локальные коммиты поверх | `git pull --rebase` | Нормальная практика для **ещё не запушенных** коммитов |

## stash

`stash` временно убирает незакоммиченные изменения, чтобы освободить рабочий каталог.

| Команда | Назначение | Пример | Важные замечания |
|---|---|---|---|
| `git stash push -m` | Спрятать изменения с описанием | `git stash push -m "WIP: форма входа"` | Просто `git stash` тоже работает, но без описания через неделю не вспомнить, что внутри |
| `-u` | Включить неотслеживаемые файлы | `git stash push -u -m "с новыми файлами"` | По умолчанию новые файлы остаются в рабочем каталоге |
| `git stash list` | Список сохранённого | `git stash list` | `stash@{0}` — самое свежее |
| `git stash show -p` | Посмотреть содержимое | `git stash show -p stash@{1}` | |
| `git stash apply` | Вернуть изменения, оставив запись в списке | `git stash apply stash@{1}` | Безопаснее `pop`: при конфликте запись не потеряется |
| `git stash pop` | Вернуть и удалить из списка | `git stash pop` | При конфликте запись **не** удаляется: после разрешения удалите её сами через `drop` |
| `git stash branch` | Создать ветку из stash | `git stash branch feature/wip stash@{0}` | Полезно, если основная ветка ушла далеко вперёд |
| `git stash drop` | Удалить одну запись | `git stash drop stash@{0}` | ⚠️ **Опасно:** восстановить можно только по хешу, который печатается при удалении |
| `git stash clear` | Удалить все записи | `git stash clear` | ⚠️ **Опасно:** удаляет все сохранённые изменения. Восстановление крайне затруднительно |

## restore reset revert clean

Главное правило выбора:

| Задача | Команда | Безопасность |
|---|---|---|
| Убрать файл из индекса, но сохранить правки | `git restore --staged файл` | Безопасно |
| Отбросить правки в файле | `git restore файл` | ⚠️ Необратимо |
| Отменить последний локальный коммит, сохранив изменения | `git reset --soft HEAD~1` | Безопасно для изменений |
| Отменить **запушенный** коммит | `git revert ХЕШ` | Безопасно: создаёт новый коммит |
| Вернуть ветку точно к состоянию `origin` | `git reset --hard origin/main` | ⚠️ Необратимо для незакоммиченного |
| Сдвинуть ветку, сохранив черновик | `git reset --keep HEAD~1` | Откажется, если черновик пересекается со сбрасываемым коммитом |
| Удалить неотслеживаемые файлы | `git clean -fd` | ⚠️ Необратимо. `reset --hard` неотслеживаемые файлы **не** удаляет |

| Команда | Назначение | Пример | Важные замечания |
|---|---|---|---|
| `git restore --staged` | Убрать из индекса (unstage) | `git restore --staged .env` | Изменения в файле остаются |
| `git restore файл` | Вернуть файл к версии из индекса | `git restore src/app.py` | ⚠️ **Опасно:** незакоммиченные правки в файле удаляются без возможности восстановления |
| `git restore .` | Отбросить все правки в рабочем каталоге | `git restore .` | ⚠️ **Опасно:** то же самое для всех файлов. Если сомневаетесь — сначала `git stash` |
| `git restore --source` | Взять версию файла из другого коммита | `git restore --source=HEAD~3 -- config.yml` | ⚠️ Текущая версия файла в рабочем каталоге будет заменена |
| `git reset --soft` | Сдвинуть ветку, изменения оставить в индексе | `git reset --soft HEAD~1` | Удобно, чтобы переделать последний коммит |
| `git reset` (`--mixed`) | Сдвинуть ветку, изменения оставить в рабочем каталоге | `git reset HEAD~1` | Режим по умолчанию. Без аргументов просто очищает индекс |
| `git reset --hard` | Сдвинуть ветку и **перезаписать** рабочий каталог | `git reset --hard HEAD~1` | ⚠️ **Опасно:** незакоммиченные изменения в **отслеживаемых** файлах уничтожаются. Неотслеживаемые файлы остаются; их удаляет `git clean`. Коммиты можно вернуть через `reflog`. Для уже запушенных коммитов используйте `revert` |
| `git reset --keep` | Как `--hard` для указателя ветки, но незакоммиченные правки сохраняет | `git reset --keep HEAD~1` | Если правки пересекаются со сбрасываемым коммитом, команда откажется и ничего не испортит |
| `git revert` | Создать коммит, отменяющий указанный | `git revert a1b2c3d` | Историю не переписывает, поэтому подходит для общих веток. Для merge-коммита: `git revert -m 1 ХЕШ` |
| `git clean -n` | Показать, какие неотслеживаемые файлы будут удалены | `git clean -nd` | Сухой прогон, ничего не удаляет. Всегда запускайте перед `-f` |
| `git clean -fd` | Удалить неотслеживаемые файлы и каталоги | `git clean -fd` | ⚠️ **Опасно:** файлы удаляются с диска, их нет ни в Git, ни в корзине. `-x` удалит и игнорируемые (`.env`, `.venv`) |

## remote fetch pull push

| Команда | Назначение | Пример | Важные замечания |
|---|---|---|---|
| `git remote -v` | Список удалённых репозиториев | `git remote -v` | |
| `git remote add` | Добавить remote | `git remote add origin git@github.com:user/repo.git` | Для форков обычно добавляют ещё `upstream` — исходный репозиторий |
| `git remote set-url` | Сменить адрес | `git remote set-url origin git@github.com:user/repo.git` | Например, чтобы перейти с HTTPS на SSH |
| `git remote remove` | Удалить remote | `git remote remove old` | Удаляет только ссылку у вас, сам репозиторий на сервере не трогает |
| `git fetch` | Скачать изменения, ничего не сливая | `git fetch --all --prune` | Безопасно всегда. `--prune` удаляет ссылки на ветки, удалённые на сервере |
| `git pull` | `fetch` + `merge` (или `rebase`) в текущую ветку | `git pull` | При расхождении веток без настройки `pull.rebase` Git попросит выбрать стратегию |
| `git pull --ff-only` | Обновиться, только если не нужно сливать | `git pull --ff-only` | Самый предсказуемый вариант для `main` |
| `git push` | Отправить коммиты | `git push` | Отклонён (`rejected`, `non-fast-forward`)? Значит, на сервере есть новые коммиты: сначала `git pull` |
| `git push -u origin ветка` | Первая отправка новой ветки и связь с ней | `git push -u origin feature/login` | После `-u` достаточно писать просто `git push` |
| `git push --force-with-lease` | Перезаписать удалённую ветку после rebase или amend | `git push --force-with-lease` | ⚠️ **Опасно:** заменяет историю на сервере. Откажет, если там появились чужие коммиты, которых вы не видели |
| `git push --force` | Перезаписать без проверок | `git push -f` | ⚠️ **Очень опасно:** молча уничтожает чужие коммиты на сервере. Используйте `--force-with-lease`. Никогда не применяйте к `main` |
| `git push origin --delete` | Удалить ветку на сервере | `git push origin --delete feature/old` | ⚠️ **Опасно:** ветка пропадёт у всех. Восстановить можно, только если у кого-то остались её коммиты |
| `git push --tags` | Отправить теги | `git tag v1.0.0 && git push origin v1.0.0` | Теги не отправляются обычным `push` |

## Конфликт слияния

Конфликт возникает, когда две ветки по-разному изменили одни и те же строки или одна ветка удалила файл, который другая изменила. Это нормальная ситуация, а не ошибка. Git останавливается и просит человека решить, каким должен быть результат.

Воспроизвести конфликт в одноразовом репозитории: `bash examples/git/conflict_demo.sh` (с `KEEP=1` репозиторий сохранится для экспериментов).

### Как выглядит конфликт

```text
$ git merge feature
Auto-merging config.txt
CONFLICT (content): Merge conflict in config.txt
Automatic merge failed; fix conflicts and then commit the result.

$ git status --short
UU config.txt
```

Внутри файла:

```text
<<<<<<< HEAD
timeout=45
=======
timeout=60
>>>>>>> feature
retries=3
```

- Между `<<<<<<< HEAD` и `=======` — версия текущей ветки (**ours**, «наша»).
- Между `=======` и `>>>>>>> feature` — версия вливаемой ветки (**theirs**, «их»).
- При `merge.conflictStyle=zdiff3` между ними появится блок `|||||||` с версией общего предка. По нему видно, что именно поменяла каждая сторона.

### Пошаговое разрешение

1. **Остановитесь и посмотрите на масштаб:**
   ```bash
   git status
   git diff --name-only --diff-filter=U    # только файлы с конфликтами
   ```
2. **Откройте каждый файл** и приведите участок к нужному виду: оставьте одну из версий, объедините их или напишите новую. Удалите **все** маркеры `<<<<<<<`, `=======`, `>>>>>>>`. VS Code и Cursor показывают кнопки *Accept Current / Incoming / Both*.
3. **Если нужна целиком одна сторона**, берите её из соответствующего коммита — так обновляются и рабочая копия, и индекс, и конфликт по файлу сразу считается разрешённым:
   ```bash
   git restore --source=HEAD --staged --worktree -- path/file        # текущая ветка
   git restore --source=MERGE_HEAD --staged --worktree -- path/file  # вливаемая ветка
   ```
   Короче и с тем же эффектом: `git checkout HEAD -- path/file` и `git checkout MERGE_HEAD -- path/file`.

   `git restore --ours/--theirs` для этого **не подходит**: они копируют только рабочее дерево и **не** снимают конфликт в индексе. Сочетание `--ours --staged` Git отвергает (`fatal: '--ours' or '--theirs' cannot be used with --staged`). После них всё равно нужен `git add`.

   Если одна сторона **удалила** файл, а другая изменила (`UD` или `DU` в `git status --short`):
   ```bash
   git rm  path/file     # принять удаление
   git add path/file     # оставить файл текущей ветки
   ```
4. **Проверьте, что маркеров не осталось**, и запустите тесты:
   ```bash
   git diff --check                     # подсветит оставшиеся маркеры и лишние пробелы
   grep -rnE '^(<<<<<<<|=======|>>>>>>>)' . --exclude-dir=.git
   ```
5. **Завершите слияние.** Если в шаге 3 использовали `--staged --worktree` (или `git checkout HEAD/MERGE_HEAD --`), файл уже в индексе — достаточно:
   ```bash
   git merge --continue      # или git commit --no-edit
   ```
   Если правили файл вручную, сначала `git add path/file`.
6. **Передумали?** `git merge --abort` вернёт всё к состоянию до слияния.

| Команда | Назначение | Пример | Важные замечания |
|---|---|---|---|
| `git diff --name-only --diff-filter=U` | Список файлов с конфликтами | — | `U` — unmerged |
| `git diff` во время конфликта | Комбинированный дифф обеих сторон | `git diff path/file` | |
| `git restore --source=HEAD --staged --worktree` | Взять текущую ветку целиком и снять конфликт | `git restore --source=HEAD --staged --worktree -- config.yml` | ⚠️ Правки вливаемой ветки в этом файле будут отброшены. Эквивалент: `git checkout HEAD -- config.yml` |
| `git restore --source=MERGE_HEAD --staged --worktree` | Взять вливаемую ветку целиком и снять конфликт | `git restore --source=MERGE_HEAD --staged --worktree -- config.yml` | ⚠️ Правки текущей ветки в этом файле будут отброшены. Во время rebase вместо `MERGE_HEAD` используйте `REBASE_HEAD` |
| `git rm` / `git add` при `UD`/`DU` | Принять удаление или оставить файл | `git rm path/file` | `git restore --theirs` при удалении «у них» может стереть файл с диска, но конфликт в индексе останется |
| `git mergetool` | Открыть внешний инструмент слияния | `git mergetool` | Инструмент задаётся через `merge.tool` |
| `git merge --abort` | Отменить слияние | — | Работает, пока слияние не завершено |
| `git rebase --abort` | Отменить rebase | — | |
| `git log --merge -p` | Коммиты, которые привели к конфликту | `git log --merge -p -- path/file` | Помогает понять, зачем каждая сторона меняла код |
| `git config rerere.enabled true` | Запоминать решения конфликтов | — | Повторный такой же конфликт Git разрешит сам |

> [!IMPORTANT]
> Во время **rebase** берите сторону так: `HEAD` — ветка, **на которую** вы переносите коммиты; `REBASE_HEAD` — **ваш** коммит, который сейчас применяется. Имена `--ours`/`--theirs` здесь перепутаны относительно merge: `--ours` указывает на `HEAD` (базу rebase). Не используйте `MERGE_HEAD` во время rebase — этой ссылки нет. Перед выбором стороны перепроверьте содержимое: `git show HEAD:path` и `git show REBASE_HEAD:path`.

Как реже попадать в конфликты: делайте небольшие ветки и часто вливайте в них `main` (`git merge origin/main` или `git rebase origin/main`). Не смешивайте в одном коммите массовое переформатирование и изменения логики. Договоритесь о форматтере и окончаниях строк.

## Восстановление и reflog

`reflog` — локальный журнал всех перемещений `HEAD`: коммитов, `reset`, `rebase`, переключений веток. Записи хранятся около 90 дней (для недостижимых коммитов — около 30). Это главный способ спасения после неудачного `reset --hard`, `rebase` или `branch -D`.

| Команда | Назначение | Пример | Важные замечания |
|---|---|---|---|
| `git reflog` | История перемещений `HEAD` | `git reflog -n 20` | Только локальный: на сервер не отправляется и при клонировании не копируется |
| `HEAD@{N}` | Состояние N шагов назад | `git show HEAD@{2}` | |
| Вернуть ветку | Отменить неудачный reset или rebase | `git reset --hard HEAD@{1}` | ⚠️ Незакоммиченные изменения при этом будут потеряны: проверьте `git status` |
| Восстановить удалённую ветку | Создать ветку на найденном коммите | `git branch restored a1b2c3d` | Хеш возьмите из `git reflog` или из вывода `git branch -D` |
| `git fsck --lost-found` | Найти «висящие» коммиты, которых нет в reflog | `git fsck --lost-found` | Последний шанс, например, для удалённого stash |

Незакоммиченные изменения, отброшенные через `restore`, `reset --hard` или `clean`, **reflog не спасёт**. Если сомневаетесь — сделайте `git stash` или временный коммит.

| Шаблон в `.gitignore` | Что игнорирует |

| Команда | Назначение | Пример | Важные замечания |
|---|---|---|---|

## Практические сценарии

**1. Начать проект и отправить на GitHub.**

```bash
git init -b main
git add -A && git status          # проверить, что не попало лишнее
git commit -m "Первый коммит"
git remote add origin git@github.com:user/repo.git
git push -u origin main
```

**2. Типичный цикл работы над задачей.**

```bash
git switch main && git pull --ff-only
git switch -c feature/search
# ... правки ...
git add -p && git commit -m "Добавить поиск по тегам"
git fetch && git rebase origin/main     # подтянуть свежий main (ветка ещё не запушена)
git push -u origin feature/search
```

**3. Закоммитил не в ту ветку (ещё не запушено).**

```bash
git branch feature/right          # сохранить коммит в новой ветке
git reset --keep HEAD~1           # сдвинуть main; черновик в других файлах сохранится
git switch feature/right
```

`--hard` вместо `--keep` уничтожит незакоммиченные правки в отслеживаемых файлах.

**4. Исправить сообщение или добавить забытый файл в последний коммит (ещё не запушено).**

```bash
git add forgotten.py
git commit --amend -m "Новое сообщение"
```

**5. Срочно переключиться на другую задачу.**

```bash
git stash push -u -m "WIP: поиск"
git switch hotfix
# ... исправление, коммит ...
git switch -
git stash pop
```

**6. Отменить уже запушенный коммит.**

```bash
git revert a1b2c3d     # новый коммит, отменяющий изменения
git push
```

**7. Синхронизировать форк с исходным репозиторием.**

```bash
git remote add upstream https://github.com/original/repo.git
git fetch upstream
git switch main && git merge --ff-only upstream/main
git push
```

**8. Сделал `reset --hard` и потерял коммиты.**

```bash
git reflog                        # найти строку до reset, например HEAD@{1}
git reset --hard HEAD@{1}         # или: git branch rescue <хеш>
```

Тренировка без риска: `bash examples/git/undo_demo.sh`.

## Частые ошибки

| Ошибка | Что происходит | Как правильно |
|---|---|---|
| `git push` → `rejected (fetch first)` | На сервере есть коммиты, которых нет у вас | `git pull` (или `git pull --rebase`), разрешить конфликты, снова `git push` |
| `fatal: Need to specify how to reconcile divergent branches` | Ветки разошлись, а стратегия `pull` не задана | `git pull --rebase` или `git pull --no-rebase`. Либо один раз задать `pull.rebase` |
| `git push --force` после rebase общей ветки | ⚠️ Коммиты коллег исчезают с сервера | Не делать rebase общих веток, использовать `--force-with-lease` |
| `.env` или ключи в коммите | Секрет остаётся в истории даже после удаления файла | Немедленно отозвать и сменить секрет, добавить файл в `.gitignore`. Чистить историю — через `git filter-repo` |
| `git add .` без проверки | В репозиторий попадают `node_modules`, `.venv`, логи, большие файлы | Сначала `.gitignore`, потом `git status`, затем `git add` |
| Работа в «detached HEAD» | Новые коммиты не принадлежат ни одной ветке и легко теряются | `git switch -c новая-ветка`, чтобы сохранить их |
| Оставленные маркеры `<<<<<<<` | Код не компилируется, конфиг ломается | `git diff --check` перед коммитом, поиск маркеров через `grep` |
| `git reset --hard` «на всякий случай» | ⚠️ Незакоммиченная работа исчезает безвозвратно | `git stash` или `git restore --staged` по ситуации |
| Путаница `ours`/`theirs` при rebase | Остаётся не та версия файла | При rebase брать `HEAD` (база) и `REBASE_HEAD` (ваш коммит), а не `--ours`/`--theirs` |
| Неверный автор коммитов | `user.email` не совпадает с аккаунтом | `git config --global user.email ...`. Последний коммит: `git commit --amend --reset-author --no-edit` |
| `LF will be replaced by CRLF` и «изменены все строки» | Разные настройки окончаний строк у участников | `.gitattributes` в репозитории, затем `git add --renormalize .` |
| Огромный бинарный файл в истории | Репозиторий раздувается, push отклоняется | Git LFS для больших файлов. Уже закоммиченное — `git filter-repo` |
| `error: pathspec 'x' did not match` при `switch` | Ветки нет локально, а ссылки на удалённые ветки устарели | `git fetch`, затем `git switch x` |
